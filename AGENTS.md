# Festival totem: AI handoff and project status

Last reviewed: 2026-09-23. Read this file first when resuming work; inspect current code and the two detailed documents before changing behavior. ## Goal and current priority

Build a portable, battery-powered festival totem with two opposite-facing HUB75 LED panels, GIFs, graphics/text overlays and transitions, music-reactive visuals, and phone controls that feel like a live instrument. Hardware assembly and travel are imminent. Current priority: finish a reliable physical build, validate the MatrixPortal S3 performance, then refine Vibe/Chaos interaction using real bass-heavy music. The user prefers direct progress and a simple phone UI with safe scrolling.

## Settled decisions

- Two physical **32×64 panels oriented landscape** are logically **64×32 each**, back to back. The MatrixPortal S3 drives them as one chained 128×32 HUB75 output; front and back retain logical identities. Physical back rotation, color order (an RBG quirk was noted), scan compatibility, IN/OUT order, and actual mapping need the real panels and smoke test.
- Front/back can currently be controlled independently or linked. For performance and the physical goal, matching content on both sides is an attractive option, but do not remove independent functionality without checking with the user. Linking control does not automatically imply a single GIF decoder/frame render; measure it.
- Mac/desktop is the authoring environment; CircuitPython MatrixPortal S3 is the target player. GIF crop, fit, positioning, color work, dithering and thumbnails are prepared on the Mac and baked to native 64×32 files. The board should stream prepared media, render lightweight effects/overlays, serve the compiled phone page and accept compact commands. See `MATRIXPORTAL_DEPLOYMENT.md`.
- The phone UI should be safe while scrolling. Active selection is indicated with a small dot beside text instead of filling the entire button. The random GIF button reads **Shuffle**. The four starting Vibe presets **Pulse, Spark, Neon, Chaos** are editable, renameable, addable and deletable, including the defaults; settings are saved in the phone browser's localStorage (not on the board). Do not reintroduce sample-hit/tap-signal audition controls for the audio analyzer.
- Phone microphone analysis is the current implemented input: browser Web Audio creates normalized Energy/Low/Body/Bright/Pulse signals and sends compact `audio_frame` messages. It requires the phone browser and mic permission to remain active. Audio analysis is deliberately awaiting tests on a representative bass system; do not assume current calibration is final. The physical I²S microphone is a planned alternate source, not an integrated on-board analyzer yet. Keep the normalized runtime audio interface so either source can drive the visuals.
- Optional joystick/game controller input is a future playability feature, not a prerequisite. An ADS1015 I²C converter was discussed as a way to read an analog joystick while reserving S3 pins for microphone and microSD. Do not assume joystick, ADS1015, microphone, or microSD are already wired or supported by running firmware.
- Wi-Fi phone control and local API are part of the architecture. Future access control or device AP mode is an idea; neither is enabled now.
- Performance should be assessed on **physical hardware**: baseline matrix alone; GIF decoding; mirrored versus independent sides; overlay and transition layers; audio/Chaos; HTTP load; then combinations. Log FPS, free RAM, decode/render/present and HTTP/audio timings, long frame or loop spikes, missed deadlines, voltage/current and battery runtime. No representative hardware benchmark data exists yet.

## Power and wiring decision (latest)

The working plan is UGREEN USB-C PD battery → PD trigger → TOBSUN EA50-5V 50 W buck → main fuse → DC switch → 5 V distribution. The two panel power connectors each receive their own parallel 5 V/GND branch. The user has **ordered a 5 V/5 A USB-C male-to-bare-wire power pigtail**, intended as a **third 5 V/GND distribution branch feeding the MatrixPortal S3 USB-C input**. This supersedes the older separate-battery-port controller feed described in previous revisions of `HARDWARE_ARCHITECTURE.md`. Cable rating is capacity, not imposed board current. Verify cable polarity, actual 5 V output, USB-C power-in behavior and branch protection on the bench before final assembly. Use the buck's **output** terminals for all 5 V branches; the PD-trigger side is higher voltage. The buck label says **12 V/24 V input, 5 V 10 A max output**; the trigger offers 5/9/12/15/20 V. Confirm the converter's supported input range and actual PD trigger voltage under load before using 20 V; the photo label alone does not settle intermediate-voltage compatibility. A 5 V/10 A supply may be tight for two bright panels, so cap brightness and measure power. The MatrixPortal's panel mounting terminals are USB-fed **outputs**, not the controller power input. Do not power the controller through HUB75.

The intended parts also include a main fuse (8–10 A was proposed, **not a validated final size**), DC-rated switch and distribution block. A branch fuse suitable for the controller pigtail is desirable because a system fuse sized for panels may not protect a thin branch. Detailed build/testing sequence is in `HARDWARE_ARCHITECTURE.md`.

## Code map

- `simulator.py`: Pygame desktop entry point (64×32 front/back), runs `TotemRuntime` and desktop HTTP controller on port 8765.
- `totem_runtime.py`: platform-neutral state, phone command routing, two side controllers, slideshow/scene logic and rendering orchestration. `visual_engine.py`, `transition_engine.py`, `text_engine.py`, `overlay_engine.py`, `chaos_engine.py`, `particles.py`, `effects.py`: visual layers and effects.
- `runtime_io.py`: display interfaces and normalized `SignalStore` for phone audio/motion and possible future hardware inputs. Older wire keys `volume/bass/mids/highs/beat` map to the user-facing Energy/Low/Body/Bright/Pulse labels.
- `desktop_media.py`, `image_assets.py` and `image_display.py`: desktop media and authoring. `tools/prepare_matrixportal_assets.py` produces `matrixportal_build/` including manifest, baked GIFs and `www/index.html`.
- `controller_ui.py`: deterministic phone HTML build from `phone_server.PHONE_HTML` and an ordered transform pipeline. `audio_phone_server.py` contains browser analyzer; `performance_phone_server.py` and `performance_ui_reorg_patch.py` shape the Vibe/Chaos controls; the other `*_ui.py` / `*_patch.py` transforms handle layout, text, icons, safe sliders and screen modes. The compiled page is reused for desktop and baked deployment. Changes in the base HTML or transforms can break string anchors; inspect the assembled HTML and its tests.
- `phone_server.py` / `secure_phone_server.py`: desktop controller HTTP. `matrixportal_server.py` and `control_bus.py`: nonblocking CircuitPython HTTP and command queue; the optional access policy is not enabled.
- `matrixportal_backend.py`: single RGB565 128×32 framebuffer with 64×32 logical views and native matrix refresh. `matrixportal_media.py` / `matrixportal_library.py`: separate front/back `gifio.OnDiskGif` players with at most one scheduled decode per loop iteration. `matrixportal_smoke_test.py`: board bring-up and coarse metrics via `runtime_metrics.py`.
- `HARDWARE_ARCHITECTURE.md` and `MATRIXPORTAL_DEPLOYMENT.md`: detailed physical and deployment notes. `tests/`: desktop tests. Code in these modules does **not** establish that a complete CircuitPython app has been deployed.
